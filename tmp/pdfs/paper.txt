CHAPTER 1 
THE PROBLEM AND ITS BACKGROUND 
Introduction 
Digital technologies have changed how customers discover products, communicate 
with businesses, and place orders. Restaurant websites can provide a centralized place for 
presenting menus, displaying prices, maintaining customer accounts, and coordinating order 
information. When these functions are connected to a database and supported by role -based 
access, restaurant personnel can review incoming orders and manage their progress more 
consistently than when information is scattered across separate channels. 
Kathy’s Hub is represented in this project by a mobile -first web application for 
restaurant customers and authorized staff. The repository contains a public -facing restaurant 
website, an authenticated menu experience, a cart and demo checkout workflow, customer 
order history, and an administrative workspace for menu and order management. The 
application uses HTML, CSS, and JavaScript on the client side, an Express server built with 
Node.js, and Supabase services for authentication and persistent data storag e. The website is 
prepared for deployment through Render. 
The project is intended to organize menu browsing and order processing in one web -
based environment. Customers can review food and beverage options, select product 
variants, manage cart quantities, submit authenticated demo orders, and view order status. 
Authorized staff can review orders and move them through permitted stages. Owners or 
administrators can manage menu items and member information. The current implementation 
also provides a public event-offer page that lets users compare supplied packages and prepare 
an email inquiry. 
However, the repository explicitly identifies important limitations. Orders are marked 
as demo orders; cash-on-delivery remains unpaid in the system, online payment is simulated, 
and delivery booking is not implemented. The event inquiry page prepares a message for the 
customer to send manually and does not save the inquiry, reserve a date, collect a deposit, or 
confirm a booking. Therefore, this research describes the current system accurately and does 
not present simulated transactions as live payment or delivery services.

Background of the Study 
The project emerged from the need to present Kathy’s Hub menu and ordering-related 
information through an accessible website. A digital menu allows customers to examine a 
broad range of products, sections, and available sizes or portions before making a selection. 
The repository documentation states that the catalog was transcribed from supplied menu 
photographs and contains 120 products, 22 sections, and 169 priced options. The system 
preserves product variants such as hot and cold drink sizes, slice and w hole cheesecake 
portions, and different snack sizes. 
The website is designed for mobile -first access and includes menu search, section 
filtering, product cards, and a cart that can retain its contents across page navigation and 
refresh within the browser session. Customers must sign in to submit an order. The checkout 
workflow validates customer contact and delivery information and saves the order to 
Supabase through a server API. Order items preserve product and price snapshots so later 
menu edits do not silently rewrite the contents of an existing order. 
For management, the administrative workspace separates overview, members, menu 
management, and order management. Menu availability and product options can be 
maintained by authorized users. The order queue supports status filtering and records a 
history of status changes, including the actor, time, and note. Customers may cancel their 
own orders while the order is still pending; rejected, cancelled, and completed orders are 
terminal states. Permissions distinguish customers, staff, kitchen staff, owners, an d platform 
administrators. 
The study will document how these implemented functions address menu 
presentation, authenticated ordering, order tracking, and administrative coordination. It will 
also identify gaps that must be resolved before operational use, particularly real payment 
processing, delivery scheduling and pricing, customer notifications, refunds, inventory 
deduction, retention policies for personal data, and formal reservation management. These 
limitations are relevant to system evaluation because an interface that accepts a demo order is 
not equivalent to a fully operational restaurant delivery service.

Statement of the Problem 
This study aims to document and evaluate the Kathy’s Hub web -based restaurant 
ordering and management system based on its current implementation. It seeks to answer the 
following questions: 
1. How can the website present Kathy’s Hub products, sections, prices, and size or portion 
options in a searchable and mobile-responsive menu? 
2. How can authenticated customers create and review demo orders while maintaining 
accurate order details and price snapshots? 
3. How can authorized restaurant personnel manage menu availability and process orders 
through defined status transitions? 
4. How does the system restrict access to customer profiles, order records, and 
administrative functions according to user roles? 
5. What technical and operational limitations remain before the system can support live 
payment collection, delivery coordination, and confirmed event reservations? 
Objectives of the Study

The general objective of this study is to document and assess Kathy’s Hub, a mobile -
first web -based restaurant ordering and management system, with emphasis on menu 
presentation, authenticated demo ordering, order -status management, role -based access, and 
the limitations that must be addressed before live business deployment.

REVIEW OF RELATED LITERATURE AND STUDIES 
Related Literature 
Web-Based Information Systems in Restaurant Operations 
A web -based information system connects user -facing pages with server -side rules 
and persistent data. In a restaurant context, such a system can present menu information, 
collect customer selections, and give authorized staff a shared view of orders. The benefit 
depends on the consistency of the data and the reliability of the workflow, not merely on the 
presence of a website. Kathy’s Hub follows this pattern by separating its public pages, 
Express server routes, and Supabase-backed records. 
Digital Menus and Product Catalog Management 
A digital menu makes product information easier to browse and update than a menu 
embedded in a static document. Search and category or section filters help customers 
navigate a large catalog, while explicit variants avoid confusing a product’s size or portion 
with a separate product. The Kathy’s Hub repository documents a catalog of 120 products, 22 
sections, and 169 priced options. It also uses database constraints and server -side validation 
to reduce duplicate entries and invalid option data. 
Shopping Carts and Checkout Validation 
A cart lets users review selected products, change quantities, and estimate a subtotal 
before submission. A dependable checkout process must revalidate the product’s current 
availability and price on the server rather than trust totals supplied by a browser. The Kathy’s 
Hub implementation calculates order totals in integer centavos, checks selected options 
against the saved catalog, snapshots the items and prices, and requires customers to review a 
changed total when the catalog price no longer matches their cart. 
Authentication, Authorization, and Privacy 
Authentication identifies a user; authorization determines what that user is allowed to 
do. A restaurant application may need different privileges for customers, order -processing

staff, kitchen staff, and owners. The project uses Supabase Authentication and role 
information held in trusted application metadata. Database row -level security limits 
customers to their own order records, while administrative roles are permitted to perform 
specified management tasks. These controls are important because orders and customer 
profiles can contain contact information and delivery addresses. 
Order Lifecycle and Audit History 
Order management requires a clear set of permitted states and a record of changes. 
Without defined transitions, orders may be advanced incorrectly or conflicting updates may 
overwrite one another. The Kathy’s Hub order workflow documents the stages Pending, 
Accepted, Preparing, Ready, and Completed, along with Rejected and Cancelled terminal 
outcomes. Status changes retain actor, time, and note information, and version checks help 
reject stale concurrent updates. 
Responsive Design and Mobile Accessibility 
Responsive design adapts navigation and controls to different screen sizes. Mobile 
ordering interfaces should keep search, section selection, variant selection, and cart controls 
usable on narrow screens. The project documentation describes mobile -first menu filters, 
touch targets, and browser checks at 320 -pixel and 390 -pixel viewport widths. These 
implementation checks provide useful technical evidence, although formal user testing is still 
required to establish user satisfaction and ease of use. 
Event Package Information and Reservation Inquiries 
Digital event pages can help prospective customers compare venue rental and 
celebration packages before contacting a business. However, an inquiry form should clearly 
distinguish a request for information from a confirmed booking. Kathy’s Hub’s current event 
page states that prices are transcribed from supplied brochures, package rates may require 
confirmation, and inquiry drafts are prepared for customers to send through their own email 
application. The page does not store inquiries or reserve dates. 
Limitations of Demo Payments and Delivery Workflows 
A checkout demonstration is not equivalent to a production transaction. Live ordering 
requires clear payment states, delivery fees and coverage, dispatch coordination, customer

Research on E-Commerce Security and Access Control 
Literature on secure web applications emphasizes that access controls should be 
enforced on the server and data layer rather than relying only on hidden interface elements. 
Kathy’s Hub reflects this principle through server -side authorization, database row -level 
security, restricted column grants, order validation, and checks on legal status transitions. 
The implementation is therefore relevant as a case for examining how role separation and 
database policies support privacy and data integrity in a small-business web application. 
Research on Responsive Web Usability 
Studies of mobile web usability generally examine whether users can locate 
information, understand available choices, and complete tasks with limited effort on different 
screen sizes. The project’s mobile -first menu and cart design is intended to support these 
tasks. Existing viewport checks demonstrate that selected layouts were inspected on narrow 
screens, but they should be supplemented with task -based testing involving representative 
customers and staff before drawing conclusions about overall usability.

Synthesis 
The reviewed concepts indicate that a restaurant web system needs more than an 
attractive public website. Its menu data must remain consistent, cart totals should be verified 
at checkout, access should be limited by role, and order changes should follow defined 
transitions. Responsive design is important because customers may browse from phones, 
while clear notices are necessary when payment, delivery, or booking steps are only 
simulated or handled outside the website. 
Kathy’s Hub brings these elements together in a mobile -first web application using 
HTML, CSS, JavaScript, Node.js/Express, and Supabase. Its catalog, authentication, saved 
demo orders, role-based administrative tools, and status history provide a practical basis for 
studying an integrated restaurant workflow. At the same time, the project documentation 
shows that live payment, delivery booking, inventory deduction, notifications, refunds, and 
reservation persistence remain outside the current scope.

The system gap addressed by this project is the need to consolidate menu

Proposed System 
The proposed system, as implemented in the repository, is a mobile -first restaurant 
website with connected customer and staff workflows. Customers browse the menu, select 
product variants, maintain a cart, sign in, submit a demo order, and review order history. 
Authorized staff review the order queue and update order statuses. Owners or platform 
administrators manage the catalog and member records according to their permissions. A 
separate public event page presents supplied package information and prepares  an inquiry 
draft. 
The system is intended to improve the organization and visibility of menu and order 
information. Its present operational boundary must be made clear: the checkout is 
demonstrative, online payment is simulated, cash -on-delivery remains unpaid, the delivery 
fee is set to zero for the demo, and the event page does not create a confirmed reservation.

1. The system shall display the restaurant menu and product details to visitors. 
2. The system shall allow users to search the menu and filter items by section. 
3. The system shall display available product variants and their corresponding prices. 
4. The system shall allow signed-in customers to add products to a cart, change quantities, 
and remove items. 
5. The system shall require authentication before a customer submits an order. 
6. The server shall validate customer details, product availability, selected variants, 
quantities, and current prices before saving an order.

• Privacy: customer profile and order information should only be exposed to the user or

• Reliability: duplicate checkout retries and stale administrative updates should be handled 
safely. 
• Maintainability: menu rendering, filtering, validation, and order workflows should be 
organized into reusable modules. 
• Transparency: simulated payments and unimplemented delivery or reservation functions 
must be disclosed clearly.

Data Relationship Summary 
Each authenticated user can have a profile and saved customer -detail record. A user 
may submit multiple orders. Each order references its user and contains a snapshot of the 
customer information and selected menu items at the time of checkout. Menu items may 
contain multiple variants with their own labels and prices. The order snapshot preserves the 
transaction’s item descriptions and prices even if the live catalog is edited later. 
Relationship Description 
User → Profile One authenticated user is associated with a profile 
record. 
User → Customer Details One user can have one saved customer-details 
record. 
User → Orders One user can submit multiple order records. 
Menu Item → Variants One menu item can have zero or more selectable 
variants. 
Order → Items Snapshot An order stores a list of item/option/quantity/price 
details at submission time.

System Requirements 
Hardware Requirements 
The system is browser -based and does not require a dedicated client application. 
Minimum hardware requirements should be confirmed through actual testing; at a practical 
baseline, users need a smartphone, tablet, laptop, or desktop computer capable of running a 
modern browser and accessing the internet. Restaurant staff should use a reliable device with 
sufficient screen size for order review. 
Software Requirements 
• Client: a modern web browser with JavaScript enabled. 
• Server runtime: Node.js 22.x, as declared in package configuration. 
• Application framework: Express 5.x. 
• Backend services: a configured Supabase project with Authentication and PostgreSQL.
